# Модель данных: планы, факт, index

Читать при записи факта (задача A) и планировании (задача B). Для «что сегодня» и вопросов по ходу тренировки не нужен.

## 1. Что хранят файлы планов

Файл плана несёт ровно **две функции**. Всё, что не служит ни одной из них, — не писать: это пустая трата токенов.

1. **План для атлета — что делать.** `workout`: упражнения, веса, повторы, подходы, отдых, техподсказки. До тренировки — назначение, после — что реально сделал. `note` — только то, что нужно атлету во время тренировки: техника, порядок, ограничители (потолок RIR), конкретные развилки по ходу; обоснования выбора веса и историю прошлых тренировок не писать.
2. **Факт для тренера — что было.** `postNotes` (по подходу / упражнению / тренировке, только при необходимости): отклонения и их причина, легко/тяжело, боли — голые факты, без оценок, выводов и сравнений с прошлыми тренировками. Формулировать понятно и самодостаточно — ясно без контекста, но кратко.

Плюс тонкая машинная обвязка (идентификаторы, даты, `schedule`).

## 2. Хранение и идентификаторы

Планы и факт — раздельно: `log/man/`, `log/women/`, `log/sanya/`. Каждый план — файл с возрастающим индексом (`0001.json`, `0002.json`, …); внутри — сессии (тренировки).

Навыковый трек мужчины (стойка на руках) живёт отдельно в `log/man-skill/` и в нумерацию и статистику зала не входит — `agents/track-handstand.md`.

Каждая тренировка имеет `globalNumber` — сквозной человекочитаемый номер («Тренировка N»), уникальный и непрерывный в пределах атлета (man/women), задним числом не меняется.

`log/<пол>/index.json` — указатель, который AI ведёт (чтобы не пересчитывать по файлам):
- `activePlanId`; `currentSessionId` — ближайшая невыполненная тренировка (на ней открывается HTML); `nextGlobalNumber` — номер следующей новой тренировки;
- `plans` — по каждому плану: `planId`, `file`, `status` (`planned` / `active` / `completed`), `sessionIds`. По `sessionIds` видно, какие тренировки в каком файле, без открытия файлов.

Статус тренировки — по `currentSessionId`: раньше — выполнена, `currentSessionId` — текущая, дальше — запланирована.

## 3. Структура файла плана

Файл: `schemaVersion`, `planId`, `athlete` (`man`/`women`/`sanya`), `createdAt`, `updatedAt`, `schedule` (тип, интервал, оценка длительности), `sessions`.

Сессия: `sessionId` (уникален во всём репозитории, `M-0001-S01` / `W-0001-S01` / `S-0001-S01`), `globalNumber` (показывается в HTML), `performedAt` (дата выполнения `YYYY-MM-DD`, только у выполненных — ось дат в прогрессе), `recommendedIntervalAfterPreviousHours`, `estimatedDurationMinutes`, `focus`, `workout`.

`workout` — упражнения по порядку. Упражнение: `name`, `restSeconds`, `technique`, `variants`, при необходимости `note` (общая для упражнения).

`technique` — ключ общей инструкции по технике из `technique.json` (корень репозитория, общий для всех атлетов): постановка, растяжка/пауза, темп, допустим ли читинг, типичная ошибка. `coach.html` показывает её под упражнением свёрнутым блоком «Техника». Ставится на упражнение, а у упражнения «на выбор» — на каждый вариант, если снаряды выполняются по-разному. Разные режимы одного движения — разные ключи (`bench_heavy` для 3–5 повторов, `bench_volume` для 6+). В `note` остаётся только уникальное для этой тренировки, технику из инструкции не дублировать.

`variants` — всегда список: один вариант, если снаряд не на выбор; несколько — если на выбор. Вариант: `label` (снаряд, если на выбор), `loadBlocks`, при необходимости `note` (по этому варианту); у выполненного варианта упражнения «на выбор» — `"performed": true` (по нему страница считает статистику; без флага — первый вариант).

Подход (`loadBlock`): `weight`, `unit`, `reps`, `sets`, `rir`, при необходимости `note` (условие к этому подходу, в показе `*`) и `type: "warmup"` (разминочный, в нагрузке не учитывается; в женской программе разминка прописывается явно).

Заметки — четыре уровня (сессия / упражнение / вариант / подход), все опциональные, каждая понятна без контекста; класть на свой уровень. Два поля на каждом уровне: `note` — назначение и подсказки атлету, при записи факта не перезаписывается; `postNotes` — заметки тренера по факту (пишет задача A; в записях до июля 2026 они лежат в `note`).

## 4. Стоячая информация — один раз, не в каждом плане

План ссылается на источник, не копирует:

- профиль атлета (рост, вес, оценка жира, контекст) — `requests/man.txt` / `requests/women.txt`;
- постоянные решения по залу/упражнениям (всегда этот снаряд, упражнение убрано, постоянная альтернатива) и правило самокоррекции (когда атлет сам поднимает вес, потолок RIR) — `requests/man.txt` / `requests/women.txt`, секция «Постоянные решения».

## 5. История и legacy

`history/cycle8_*` и `*.xlsx` — неизменяемые исходники, не переписывать. `history/summary_<пол>.md` — выжимка из `cycle8_<пол>` (пиковые веса прежнего периода); задача B читает её, когда доступно меньше 4 последних микроциклов. `home/` — история периода без зала, не источник актуальных назначений. Новый факт — только в JSON `log/man/`, `log/women/`.

## 6. Синхронизация представлений

JSON в `log/man/` и `log/women/` — источник правды. После изменения JSON проверить и при необходимости обновить рендер (`coach.html` и совместимые точки входа). Не держать параллельные противоречащие версии одного плана. Проверку в браузере делает пользователь — AI не запускает браузер/сервер/скриншоты (хостинг — `agents/site.md`).

## 7. Статистика

Статистику (сводка микроцикла, прогресс) считают страницы из файлов планов — AI её не пишет. После A и B проверить, что все упражнения изменённых сессий есть в словарях `muscle-map.json` и `log/<пол>/series.json`, — `agents/stats-dictionaries.md`.
